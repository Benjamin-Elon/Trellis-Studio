# Joining garden projects <!-- NEW -->

Home offers **Join a garden project** beside Create and Open. It opens the join guide inside Garden Projects. Existing Canvas Sync join commands use the same guide when the desktop join bridge is available; their legacy dialog remains the fallback. <!-- NEW -->

Paste the complete plain-text invitation email or its Trellis invitation block. Preview validates exactly one current v2 invitation, including conventional email quoting, before creating any transport registration. It displays the claimed project name, recipient email, expiration, and whether the invitation adds a new collaborator or another computer for an existing member. Preview alone does not establish project access. <!-- NEW -->

The recipient signs into or creates/connects a Trellis identity using the existing browser account controls, confirms their display name, and submits the request. The selected identity owns the transport explicitly; the currently open project cannot select the joining identity. The sender still approves the computer through the existing signed reply workflow. Preparing an invitation releases the sender's saved, unpinned editing holds so the recipient can complete acceptance; active pinned editors retain their holds. Copying a reply and opening an email draft remain separate actions; an email handoff never means the message was sent. <!-- NEW -->

**Pending invitations** stays separate from project membership and ignores project search/distance filters. Waiting for approval, downloading, ready, expiration, and revocation have distinct states. Home shows the pending count. Transport events update progress without reloading the project browser's metadata snapshots or navigating automatically. **Open project** validates the downloaded file through the existing native opening lifecycle before completing access and registration. <!-- NEW -->

New collaborators accept and link their identity in the same Users store mutation. Their generated project credential is internal; their personal identity remains their managed login. A proven pending account remains authenticated while the native policy catches up to its save; revocation ends that provisional login. The sharing controller opens the authenticated collaboration view, acquires the existing account-change hold, and saves before the guide registers library membership. Existing members restore their prior linkage or prove their project PIN once before initial linkage. A different existing identity linkage is rejected. Self-link policy permits changing only the authenticated actor's previously empty linkage; changing credentials, access, roles, other accounts, or an existing identity is excluded. <!-- NEW -->

## Main-process interfaces <!-- NEW -->

`trellisGardenJoin` exposes `preview`, `start`, `list`, `resume`, `prepare`, and `complete`. Authenticated operations accept the expected identity and session generation. `prepare` supplies invitation completion inputs only to the window watching the verified ready project. `complete` verifies saved account linkage, reuses library import, and acknowledges completion idempotently. Public listings contain neither invitation codes nor encrypted credentials. <!-- NEW -->

`TrellisGardenHome.showProjects(ui, { focus: 'join' })` opens the guide, and `Trellis.users.finishIdentityJoin(...)` reuses existing invitation validation, PIN proof, and portable login. The sharing service's internal `resumeJoin` rebuilds the same approval reply from saved invitation metadata; it does not grant approval or create duplicate registrations. New invitation blocks add optional sender-email metadata without a protocol-version change. <!-- NEW -->

## Recovery and compatibility <!-- NEW -->

Submitted progress is journaled in `local-joins` under the owning identity's device-local profile before transport registration. It never enters synchronized catalogs. Invitation blocks are protected with the desktop's existing operating-system credential protection. The full email is not persisted. When protection is unavailable, transport progress still persists, but completion secrets remain session-only and a restart notice asks the recipient to paste the invitation again. Completion removes the retained secrets. <!-- NEW -->

Reopening or repasting resumes the same request. Transport registration is saved before its folder is created and remains pending if configuration or shutdown interrupts joining. Unrelated existing folders are never adopted or overwritten. Failed saving or library registration remains retryable; accepted account changes are retained in the open document during a retry. A completed request cannot bypass current transport revocation or saved account linkage. Expired unaccepted invitations require renewal. Old clients can continue their legacy workflow; recipients need this version for the new guide and initial identity self-link policy. <!-- NEW -->

A fresh invitation may replace an unapproved request for the same project and email while preserving its pinned trust anchor and folder. The earlier journal shows that it was superseded. Already approved accounts require their existing account or additional-device workflow. Visitor invitations qualify for computer approval through their read access even though they have no editing capabilities. <!-- NEW -->
