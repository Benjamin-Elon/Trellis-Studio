# Garden communities, protocol version 1 <!-- NEW -->

The project browser gives communities their own section, with persistent right-side folds and separate Joined gardens / Not joined gardens groups. Each community and group reports its matching/overall project count and distinct people/online counts; the top section counts communities. Unjoined listings expose available counters without downloading their canvases. <!-- NEW -->

Coordinator evidence optionally includes validated `moduleCities`, `gardenModuleCount`, `locationsComplete`, and `userCount`. Locations contain only catalog city names, country/region, and city coordinates. They support nearest-distance filtering before joining. Older evidence without these fields remains valid and has unknown distance. Location changes advance the existing evidence revision; unchanged polls do not republish evidence. Live presence and renderer member tokens never enter evidence. <!-- NEW -->

Garden communities group existing garden projects. The directory exposes garden names and descriptions without downloading their canvases. Membership follows accepted active garden access; pending invitations and temporary disconnection do not change membership. Existing project/share identifiers, personal filenames, invitations, private gardens, and ungrouped shared gardens retain their existing behavior. Community features require identity-managed collaboration version 2 gardens. <!-- NEW -->

## Main-process boundaries <!-- NEW -->

`trellis-garden-community-service.js` orchestrates directory operations and private requests. `trellis-community-protocol.js` verifies and reduces immutable signed records. `trellis-community-transport.js` connects garden evidence and access grants to the existing roster, journal, approved-device membership, and managed Syncthing transport. `trellis-metadata-channels.js` retains metadata channel configuration across daemon restart and pause/resume. These channels share the configuration mutex with garden and identity folders. <!-- NEW -->

The renderer receives only the allowlisted `trellisGardenCommunities` preload operations: list, create, update, addGarden, decideAdmission, detachGarden, describeGarden, setAdministrators, requestAccess, decideAccess, listRequests, and status notifications. Main-process code derives the acting identity and verifies garden/community authority. Signing keys, identity vault keys, device ECDH private keys, arbitrary filesystem paths, transport configuration, and internal grant methods never enter this facade. <!-- NEW -->

## Storage and authority <!-- NEW -->

Each identity stores a separate `community-data/<id>` directory with immutable signed changes, signed garden eligibility evidence, signed device encryption endpoints, and request-channel advertisements. The garden carries only its signed association/evidence and a compact directory trust/transport bootstrap under `.trellis/garden-community`; it does not carry copies of the directory journal. Signed identity registrations and queued operations stay in the private identity metadata catalog. Device encryption keys and local delivery receipts stay in the transport/local profile. <!-- NEW -->

A community genesis hash is pinned by an administrator endorsement in an already trusted garden. Garden evidence contains the coordinator membership chain from the garden's pinned genesis key, accepted identity-linked users, approved devices, garden administrator/access-manager eligibility, association generation, and evidence revision. Evidence contains no canvas objects. Community roles confer no garden access authority. <!-- NEW -->

The coordinator retains association state and verified evidence in its private transport profile. Shared sidecar projections cannot overwrite that state or supply unsigned eligibility; handoff bootstraps from verified predecessor evidence. Evidence refresh repairs corrupted shared projections from the retained signed state. <!-- NEW -->

Creating a community binds its first garden before publishing genesis. Admission requires a garden administrator's signed proposal and a community administrator's signed decision; one person with both roles can complete both. The garden coordinator serializes association changes and rejects a second community until detachment. Either administrator group can detach; existing access remains. Empty communities archive automatically, including release of pending garden bindings. <!-- NEW -->

Directory records carry schema version, stable identifiers, causal parents, logical clock, actor identity, author device, and evidence hashes. Replay orders by logical clock then code-point record ID; missing predecessors remain pending, rejected predecessors cannot authorize descendants, and equal-revision evidence has a deterministic hash tie-break. Coordinator-signed retired-signer cutoffs retain known history while rejecting new directory actions from departed members/devices. Succession chooses an eligible administrator from the earliest-admitted remaining garden, then stable identity ID, and exposes the automatic successor. <!-- NEW -->

## Private requests and durable approval <!-- NEW -->

`community-requests/<request-id>` is a separate channel containing encrypted request/decision/result messages and signed policy updates. Directory advertisements disclose routing and eligibility evidence, never request notes or responses. Each message uses a random authenticated-encryption key wrapped to approved recipient endpoints through the existing ECDH/encryption primitives; signatures and encryption bind it to the request channel. Future messages and transport recipients follow coordinator-signed access-manager eligibility updates. Already delivered data cannot be recalled. <!-- NEW -->

Requests preserve their original garden trust anchor and request-time community eligibility proof. Detachment or moving does not retarget the request. Directory access can end while the private channel continues. Encrypted vault archives in private identity metadata allow paired devices to read their own request history and relay outstanding messages without copying another device's ECDH private key. Signed permanent-retirement evidence resolves requests as unavailable. <!-- NEW -->

An approval is committed by the garden coordinator only after rechecking the current approving manager, selected existing scopes, requester devices, and garden trust chain. It uses the existing Users policy/journal, publishes approved device membership, and commits sharing configuration before issuing a signed completion receipt. Durable applied-request receipts make duplicate delivery retryable; retry cannot reactivate subsequently revoked access. A fresh approved request uses a fresh account when the previous account was disabled, avoiding restoration of old editing grants. The verified receipt adds an entitlement to the requester's existing identity library; downloading remains explicit. <!-- NEW -->

Queued means no manager acknowledgement has arrived. Pending means a manager received the request. Waiting means approval is waiting for the coordinator's durable grant. Approved, denied, and unavailable are visible in personal request history even without community membership. Peer availability can delay every stage. <!-- NEW -->

## Limits and verification <!-- NEW -->

This version targets 20–100 gardens and several hundred people. Cached picker reads reuse verified directory replay and inspect file metadata for updates; browsing does not start peers, download unjoined gardens, or inspect their canvases. Journals and private request channels currently retain history without compaction. Cold verification and peer/configuration cost grow with evidence and history, so the first-version bounds are not a claim of unlimited scale. <!-- NEW -->

Existing sharing exposes the complete approved canvas. Editing scopes control editing, not content confidentiality. Revocations take effect after propagation and cannot erase downloaded information. Coordinator unavailability delays garden association/access commits; offline directory peers delay discovery. Automatic succession may select an unexpected administrator, which the picker identifies explicitly. <!-- NEW -->

`test/trellis-garden-communities.test.mjs` exercises isolated real identity, library, journal, signing/encryption, and managed configuration services with delayed folder delivery and simulated REST transport. It covers admission, single association, detachment/archival, succession, forged authority, private messages, membership loss and restoration, explicit download, pairing/revocation, requests across moves/deletion, duplicate decisions/retries, restart, and a 100-garden/300-identity cached browsing/configuration benchmark. Picker tests cover grouping, restricted discovery, ungrouped migration, search, focus, and request forms/history. These simulations do not replace native multi-computer Syncthing or production Electron smoke verification. <!-- NEW -->

The opt-in `test/trellis-garden-communities-runtime.test.mjs` uses the bundled Syncthing binary with isolated loopback profiles and no manual folder copies. Set `TRELLIS_SYNCTHING_RUNTIME_TEST=1` to exercise offline request submission, daemon reconnection, directory membership loss through garden detachment, private response delivery, and restored membership without automatic download. The production home smoke also exercises community creation with a new first garden. <!-- NEW -->
